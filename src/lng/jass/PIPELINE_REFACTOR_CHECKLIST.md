## Что уже зафиксировано как идея

Ключевая идея рефакторинга:

> Для JASS у нас по сути одна и та же базовая работа: берём текст, строим дерево/AST, собираем импорты, считаем диагностики и прочие артефакты. Разница между «одним файлом» и «деревом импортов» не в самом анализе, а в orchestration-слое: откуда пришёл текст, какие side effects разрешены, нужно ли каскадно перепарсивать соседей, нужно ли только symbols, можно ли мутировать глобальные кэши, и т.д.

Отсюда целевое направление:

- не держать несколько почти одинаковых JASS-путей анализа;
- вынести **единый JASS analysis core**;
- оставить сверху несколько **оркестраторов/режимов**, а не плодить дублирующую бизнес-логику;
- не сваливаться в «один мегаметод с россыпью случайных bool-флагов»;
- если и нужны режимы, то задавать их **явными типами / сценариями**, а не плохо совместимыми флагами.

## Что именно сейчас считается проблемой

Сейчас логика JASS-анализа размазана по нескольким местам и частично дублируется:

- `src/lng/jass/parse.rs`
  - основной in-memory parse;
  - disk parse;
  - сбор diagnostics / symbols / snapshot;
  - каскадные решения;
  - часть JASS-specific side effects.
- `src/util/parse.rs`
  - общий каркас cascade;
  - `ensure_file_symbols(...)`;
  - dispatch между языками;
  - часть общей import/symbol логики.
- `src/util/open.rs`
  - init/open/parse-only orchestration;
  - отдельный rescan-friendly путь.
- `src/http/ws.rs`
  - rescan делает двухпроходный сценарий:
    1. preload/init/symbol availability;
    2. полный parse.
- `src/http/api.rs`
  - `count_diagnostics_isolated(...)` делает ещё один read-only сценарий.

Проблема не в том, что это всё совсем разное.
Проблема в том, что **JASS core analysis очень похож**, но сейчас исполняется через разные ходы, из-за чего:

- тяжелее поддерживать единое поведение;
- выше шанс расхождения логики между single-file / rescan / isolated modes;
- сложно безопасно улучшать диагностику и import traversal;
- приходится помнить, в каком пути уже есть фикс, а в каком ещё нет.

## Что не нужно делать

### Не делать

- не делать один огромный `parse(...flags...)`, куда будут воткнуты десятки случайных bool-параметров;
- не пытаться в этой волне полноценно рефакторить AngelScript;
- не смешивать analysis и orchestration обратно в один неразделимый слой;
- не ломать текущий публичный контракт ради «идеальной архитектуры» одним большим unsafe rewrite.

### Разрешённый компромисс

Если где-то для совместимости понадобится временный режим/enum/adapter — это нормально,
если из него видно, что он ведёт к уменьшению дублирования в JASS, а не к росту хаоса.

## Scope этой волны

### В scope

- JASS parse pipeline;
- JASS single-file path;
- JASS tree/import traversal path;
- JASS rescan path;
- JASS isolated diagnostics path;
- выравнивание shared logic вокруг imports / visible component / imported symbols / diagnostics / snapshot assembly.

### Вне scope

- полноценный рефакторинг AngelScript;
- глубокая переделка builder-пайплайна в этой же волне;
- переписывание всего `src/util/parse.rs` за один приём без поэтапной валидации;
- косметический рефакторинг без архитектурного эффекта.

## AS: что именно делать сейчас

Для AngelScript в этой волне оставить только совместимые заглушки:

- сохранить текущие публичные точки входа;
- не пытаться переносить AS на новый полноценный pipeline вместе с JASS;
- при выделении общего каркаса предусмотреть место для AS-адаптера;
- в местах, где нужен polymorphic/shared API, допустима явная заглушка уровня:
  - `todo!("AS pipeline is out of scope for this refactor")` — только если код не вызывается в текущем сценарии;
  - либо пустой/минимальный adapter-слой без реальной миграции логики.

Важно:

> В этой волне **JASS — реальный target**, а `AS` должен остаться **не сломанной, но не переработанной заглушкой/адаптером**.

## Целевое состояние

Нужна архитектура примерно такого вида:

```text
input/source acquisition
    ↓
JASS analysis core
    ↓
analysis result / snapshot candidate
    ↓
scenario-specific apply/orchestration
```

Где:

### 1. Input/source acquisition
Отвечает только за то, **откуда** берётся текст/rope/tree:

- открытый документ;
- файл с диска;
- текст из rescan/init сценария;
- read-only isolated mode.

### 2. JASS analysis core
Одна точка, где сосредоточена общая JASS-логика:

- build AST;
- rewrite imports/directives;
- вычисление compile-time фактов, если нужно;
- извлечение imports/frozen imports;
- подготовка visible component context;
- построение imported symbols;
- cursor walk;
- сбор diagnostics / links / ref_map / symbols / semantic / colors / hints;
- вычисление того, что нужно для snapshot/cascade decision.

### 3. Scenario-specific orchestration
Отдельные сценарии сверху решают только вопросы режима:

- можно ли мутировать `PARSE_CACHE`;
- можно ли мутировать `IMPORT_GRAPH`;
- нужен ли `ensure_file_symbols(...)`;
- надо ли делать cascade;
- надо ли запускать builder diagnostics process;
- надо ли работать read-only;
- надо ли только посчитать diagnostics без store side effects.

Идея в том, что различие должно быть в **режиме применения результата**, а не в повторной ручной сборке похожего анализа в нескольких местах.

---

## Предпочтительная модель режимов

Если понадобятся режимы, то приоритет такой:

1. **enum / scenario type**;
2. небольшой config object с явными полями;
3. bool-флаги — только если они локальны и не образуют «flag soup».

Предпочтительные сценарии на уровне модели:

- `InteractiveOpenFile`
- `ClosedFileFromDisk`
- `RescanPreloadSymbols`
- `RescanFullParse`
- `IsolatedDiagnosticsReadOnly`

Названия могут поменяться, но смысл должен остаться именно таким:
**не флаговая каша, а явные сценарии исполнения**.

---

## Текущее понимание разницы между сценариями

### Single-file interactive parse
Почти весь JASS analysis нужен целиком, но:

- источник данных — память (`ROPE_MAP` / `TREE_MAP`);
- side effects разрешены;
- нужен snapshot store;
- нужен export diff;
- может понадобиться cascade;
- может понадобиться запуск builder diagnostics.

### Tree/rescan parse
Analysis почти тот же, но orchestration другой:

- сначала может идти preload/availability pass;
- затем полный parse по дереву;
- важен пакетный режим;
- каскад между файлами может быть не нужен в том же виде, что при live-edit;
- важнее контролируемый общий обход дерева.

### Isolated diagnostics
Analysis похож, но режим сильно ограничен:

- read-only;
- нельзя портить `PARSE_CACHE`/`IMPORT_GRAPH`;
- нужен только diagnostics result;
- допустимы упрощения, если они не ломают смысл изоляции.

## Рабочая стратегия рефакторинга

Рефакторинг делать **не одним большим коммитом**, а через несколько фаз, каждая из которых оставляет проект в рабочем состоянии.

Ниже — основной чеклист.

# Чеклист работ

## Фаза 0. Зафиксировать границы и терминологию

- [ ] Зафиксировать в коде/комментариях, что текущая волна работает только по JASS.
- [ ] Для AS оставить только совместимый adapter/stub path.
- [ ] Согласовать названия для `analysis core`, `scenario`, `apply/orchestration`, чтобы дальше не плодить новые сущности с пересекающимся смыслом.

### Критерий готовности

- По коду и комментариям видно, что JASS — основной target этой волны.
- Для AS нет ложного ощущения, что он тоже уже полноценно мигрирован.

---

## Фаза 1. Выделить JASS analysis result как отдельную сущность

- [ ] Выделить структуру результата анализа JASS, которая не привязана напрямую к конкретному transport path.
- [ ] Явно отделить:
  - входные данные анализа;
  - сам анализ;
  - side effects/store/apply.
- [ ] Убедиться, что в результате есть всё, что нужно минимум для:
  - snapshot store;
  - diagnostics;
  - export diff;
  - cascade decision.

### Примечание

Это не обязательно должен быть «идеально чистый immutable IR» с первого раза.
Достаточно, чтобы исчезла необходимость собирать одни и те же JASS-факты в нескольких местах по-разному.

### Критерий готовности

- После этой фазы уже можно ссылаться на единый JASS-result type.
- Новый type используется не как декоративная обёртка, а как реальный carrier результата анализа.

---

## Фаза 2. Вынести общий JASS analysis core из `src/lng/jass/parse.rs`

- [ ] Вынести общую JASS-логику анализа из монолитного `_parse(...)` в более явный core-проход.
- [ ] Сохранить текущую функциональность:
  - imports;
  - frozen imports;
  - visible component work;
  - imported symbols;
  - cursor walk;
  - diagnostics;
  - ref_map;
  - snapshot candidate.
- [ ] Не потерять cancellation checkpoints там, где они реально нужны.

### Особое внимание

Нужно следить, чтобы после выделения core не размазать по новым helper-ам побочки ещё сильнее, чем сейчас.
Идеальная цель этой фазы — **уменьшить**, а не просто переместить связанность.

### Критерий готовности

- Основной JASS-анализ больше не живёт целиком как один большой `_parse(...)` со смешанными обязанностями.
- Видно отделение core analysis от apply/store/cascade решений.

---

## Фаза 3. Разделить analysis и apply/orchestration

- [ ] Сделать явный слой применения результата анализа.
- [ ] Перенести туда решения вида:
  - store в `PARSE_CACHE`;
  - store в `file_cache`;
  - `IMPORT_GRAPH.mark_entry(...)`;
  - `IMPORT_GRAPH.recompute_entry_cache(...)`;
  - builder process spawn/cancel;
  - export diff и cascade list computation, если это именно orchestration-решение.
- [ ] Проверить, какие side effects должны остаться внутри analysis, а какие должны быть вынесены наружу.

### Критерий готовности

- Можно отдельно объяснить «что анализ посчитал» и «что orchestration сделал с результатом».
- Код это отражает напрямую, а не только на словах.

---

## Фаза 4. Перевести single-file JASS parse на новый core

- [ ] Перевести основной interactive JASS path на новый analysis core.
- [ ] Сохранить текущий контракт для live-edit/`parse_and_notify`.
- [ ] Проверить, что не сломаны:
  - diagnostics;
  - semantic tokens / inlay hints supply path;
  - export diff;
  - cascade scheduling;
  - builder diagnostics trigger.

### Критерий готовности

- Обычный JASS parse работает через новый core.
- Поведение для открытого файла не деградировало.

---

## Фаза 5. Перевести disk/closed-file JASS parse на тот же core

- [ ] Перевести `parse_from_disk(...)` на тот же core/result path.
- [ ] Убедиться, что разница между open-file и disk-file режимами осталась только в source acquisition и apply policy.
- [ ] Сохранить текущие fast-path проверки по возможности.

### Критерий готовности

- Открытый и закрытый JASS parse используют один analysis backbone.
- Disk path больше не содержит отдельную дублирующую бизнес-логику.

---

## Фаза 6. Привести `rescan` к тем же JASS-сценариям

- [ ] Разобрать rescan на явные JASS-сценарии:
  - preload symbols / availability;

- [ ] Минимизировать уникальную JASS-логику внутри `src/http/ws.rs`.
- [ ] Оставить в websocket handler orchestration, а не бизнес-анализ.

### Критерий готовности

- `rescan` не содержит отдельный «полускрытый JASS pipeline».
- Handler orchestrates, а не реализует собственную parse-архитектуру.

## Фаза 7. Привести isolated diagnostics к общей JASS-модели

- [ ] Разобрать `count_diagnostics_isolated(...)` и убрать из него лишнюю дублирующую JASS-логику.

### Критерий готовности

- [ ] Найти и схлопнуть повторяющиеся куски вокруг:

# Признаки неудачного рефакторинга

Если в процессе получится что-то из списка ниже, это знак остановиться и пересобрать решение:

- появился новый «mega parse function», который управляется пачкой плохо совместимых bool-флагов;
- JASS analysis переехал из одного файла в пять helper-ов, но по сути стал ещё менее читаемым;

- ради абстракции пришлось потерять текущие рабочие инварианты live-edit/cascade.
